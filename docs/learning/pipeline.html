Pipeline Walkthrough

System map

cassie-indexer is a standalone service: X timelines in, structured trade ideas out, Postgres in the middle. It borrows venue search concepts from the cassie monorepo but holds no execution keys — indexing is its entire job. Sources live in data/twitter_sources.json (~80 tracked accounts) and are seeded into the sources table.

The two-stage shape

Stage 1 — Collector (src/collector/): for each tracked source, fetch tweets since the per-source cursor (since_id), land them in raw_posts keyed on tweet_id, advance the cursor. No LLM, no market calls.
↓ decoupled by the database ↓
Stage 2 — Processor (src/processor/): drain raw_posts where status='pending' through gate+extract → route → price, persisting after each sub-step.

Why the split: the two stages run at different speeds and fail for different reasons. If the LLM or a market API breaks, the tweets are already durably landed; if X breaks, the backlog still drains. Reprocessing with new extraction logic reads from raw_posts — it never re-spends X API quota (the scarce, paid resource).

Processor internals

⓪ Thread assembly + reply policy (thread.ts) — a post is expanded into its full self-author reply chain (walk up reply_to_tweet_id to the root, BFS same-author descendants, order by time), extracted as ONE unit anchored to the root — so a thesis across tweets yields one idea, not duplicates + orphan fragments. Replies to other people are skipped entirely (root is a reply-to-others → no LLM call); only originals, quotes, and self-threads reach extraction. Idempotent: reprocessing (or a thread growing across hourly runs) deletes prior ideas for every member first.
① Gate + extract (extract.ts) — ONE structured gpt-5.4-mini call over the assembled thread returns either is_idea:false or 0..n ideas. The system prompt is the project's north-star definition, and it labels context by relationship (self-thread continues the author's own view; a reply-to-others only counts if the author states their own side). The same extractor call has OpenAI web search available, but only after the post clears the idea bar: search resolves ambiguous subjects, fresh context, and candidate tickers; it never supplies the author's evidence or direction. After the call, quotes are mechanically checked as substrings of the thread text — an idea whose evidence isn't verbatim is dropped.
② Route (route.ts) — deterministic candidate gathering (venue adapters validate real instruments) then ONE bounded LLM ranking call. The model picks among validated candidates or declares unrouted; it cannot invent instruments. The same call emits the pipeline: the derivation chain from the author's words to the chosen instrument, as ordered steps each tagged basis: quote | market | inference.
③ Price (price.ts) — entry price at posted_at is stored as the historical baseline. Current price is fetched live by the read API, not read from route_pricing.
④ Finalize — post marked processed with ideas_extracted count.

Presentation fields: context + pipeline

Two fields shape the ETH idea into a paste.trade-style card, both produced by calls we already make:

context (from the extract call) — the jargon-free explainer:

"ETH/BTC is the price ratio between Ethereum and Bitcoin. It shows how Ethereum
 is doing relative to Bitcoin, rather than just in absolute dollar terms.
 Traders use it to express a bet on one crypto outperforming the other."

pipeline (from the route call) — the provenance-tagged derivation chain:

explanation: "Author is explicitly bullish ETH/BTC and says to long ETH, which
              maps best to a long ETH perp rather than BTC."
steps:
  [quote]     "ETH/BTC has based and reclaimed the range, rotation starting."
  [quote]     "'long ETH here' and calls it 'the trade into Q3.'"
  [market]    "Venue-validated candidates are single-asset ETH/BTC perps, not the ratio."
  [inference] "Map the ratio-bullish view to a direct long ETH; BTC wouldn't express outperformance."
Naming: the routes.pipeline column (a per-idea derivation chain) is unrelated to "the pipeline" as the collector→processor system flow. Same word, two scopes.

Data model (status machines)

raw_posts.status    pending → processed | failed
trade_ideas.status  extracted → routed → priced
                              ↘ unrouted
routes.status       routed | unrouted (+ unrouted_reason)

Every idea records extractor_version + model; every route records router_version — reprocessing is auditable.
